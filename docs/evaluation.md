# Evaluation

System-level evaluation. Prompt-level evaluation (construction, injection containment, narrative
rule enforcement, live extraction accuracy) is in `docs/prompt_engineering.md` and
`scripts/evaluate_prompts.py`; the A/B comparison of the two extraction prompts is in
`scripts/compare_extraction_prompts.py`. The three are kept separate so nothing is measured twice.

| script | writes |
|---|---|
| `python scripts/evaluate.py [--mode mock\|live]` | `outputs/evaluation_report.json`, `outputs/evaluation_results.csv` |
| `python scripts/evaluate_prompts.py [--mode mock\|live] [--delay N]` | `outputs/prompt_evaluation.json` |
| `python scripts/compare_extraction_prompts.py [--mode mock\|live]` | `outputs/prompt_comparison.json` |

The evaluation date is fixed (2026-11-12) so duration-based results are reproducible.

## Evaluation dataset and ground-truth preparation

Everything is synthetic. The people, companies and universities do not exist; no real CV was
used at any point.

| dataset | size | how ground truth was prepared |
|---|---|---|
| `data/evaluation/matching_cases.json` | 5 candidate/JD cases, 35 requirement labels | each requirement's expected status written by hand from the profile and the JD, before running the engine |
| `data/evaluation/simulated_llm_outputs.json` | 6 model responses with known defects | each fixture written to contain one specific defect, with the expected validation decision recorded alongside |
| `data/evaluation/simulated_narratives.json` | 6 narratives, 11 planted violations | each violation planted deliberately and labelled by type |
| `data/evaluation/extraction_ground_truth.json` | 4 synthetic CVs | fields read off the generated PDFs by hand |
| `data/sample_cvs/` | 4 PDFs | generated by `scripts/make_sample_cv.py`: clean, ambiguous, sparse, prompt-injection |

The five matching cases cover the scenarios the assignment asks for: a candidate meeting most
requirements, one partially meeting them (with *proven* shortfalls, so `not_met` is earned), one
with missing information, one whose undated roles correctly block a `not_met`, and one with a
long but **irrelevant** career. Invalid and unreadable documents are covered by the error-path
cases; prompt injection is covered by `synthetic_cv_04_injection.pdf` and by the probes in
`evaluate_prompts.py`.

## Metrics and formulas

- **Requirement-level accuracy** = correct status labels ÷ total labels, over all cases.
- **Per-status precision** = correct predictions of status *s* ÷ all predictions of *s*;
  **recall** = correct predictions of *s* ÷ all true *s*.
- **Exact-match cases** = cases where every requirement label is correct.
- **Hallucination containment** = fabricated items dropped by grounding ÷ fabricated items planted.
- **Genuine retention** = genuine items kept ÷ genuine items present (the counterweight: a layer
  that drops everything would score 1.0 on containment alone).
- **Validation decisions correct** = fixtures whose accept/reject decision matched expectation.
- **End-to-end success rate** = runs returning a `ScreeningResult` ÷ runs attempted.
- **Error-path correctness** = malformed inputs producing the expected structured error code.
- **Extraction precision/recall** (live only) = per field, against the hand-written ground truth;
  `unsupported` lists predicted items that are not in the ground truth.

## What is measured, and what deliberately is not

| Dimension | How | Where |
|---|---|---|
| Matching quality | 5 hand-labeled cases, 35 requirement labels | `evaluate.py` |
| Validation reliability | 6 simulated LLM outputs with known defects | `evaluate.py` |
| Hallucination containment | fabricated items planted in simulated outputs | `evaluate.py` |
| System reliability | end-to-end runs on 4 synthetic CVs + 3 error paths | `evaluate.py` |
| Prompt construction & injection containment | 14 checks on rendered prompts | `evaluate_prompts.py` |
| Narrative rule enforcement | 6 simulated narratives, 11 planted violations | `evaluate_prompts.py` |
| Prompt v1 vs v2 construction | controlled-configuration + rule checks | `compare_extraction_prompts.py` |
| Extraction quality | field-level comparison vs hand-written ground truth | `evaluate_prompts.py --mode live` |
| Prompt v1 vs v2 extraction quality | both versions, same CVs, same model | `compare_extraction_prompts.py --mode live` |

Extraction quality is **not** measured in mock mode on purpose: the mock profile is a fixture
written to match the sample CV, so scoring it against ground truth would be circular and would
overstate quality. Both reports say so explicitly instead of printing a misleading number.

## Measured results (mock mode, development environment, 2026-11-12)

All numbers below are actual outputs of the scripts, not estimates. Per-case rows:
`outputs/evaluation_results.csv`.

**Matching quality** — requirement-level accuracy **1.000** (35/35 labels, 5/5 cases exact).

| status | precision | recall | support |
|---|---|---|---|
| met | 1.0 | 1.0 | 13 |
| not_met | 1.0 | 1.0 | 2 |
| unknown | 1.0 | 1.0 | 20 |

Note the shape of the support column: 20 of 35 labels are `unknown`. That is the system working
as designed — absence of evidence is not evidence of absence — and it is also why accuracy alone
would be a weak metric here, which is why per-status precision and recall are reported.

**Validation reliability** — **6/6** fixtures decided correctly: faithful and defective-but-well-formed
outputs accepted; malformed JSON, smuggled protected attributes (`age`, `gender`), and wrong
field types all rejected by the schema.

**Hallucination containment** — **4/4** fabricated items dropped by the grounding layer (a skill
with invented evidence, a skill with no evidence, an invented certification, and a real role
whose evidence was paraphrased rather than quoted — unverifiable counts as unsupported);
**9/9** genuine items kept; every drop reported as a grounding issue. A wrong `full_name` was
also dropped.

**System reliability** — end-to-end success **4/4** CVs, mean **0.004 s** per run (mock mode;
timings exclude real API latency, which dominates in live mode). On the ambiguous, sparse and
injection CVs the mock profile is grounded away, yielding an empty profile, all-`unknown`
assessments and `insufficient_information` — the designed honest behaviour, not a crash. Error
paths **3/3**: non-PDF bytes, corrupt PDF and empty upload each produced the expected structured
error code.

## Measured results (live mode)

The committed `outputs/evaluation_report.json` and `outputs/evaluation_results.csv` are from a
live run against the real Gemini API. Two things differ from mock mode, and only two: the
matching, validation and grounding figures above are identical in both modes, because none of
those components calls a model.

| metric | live | mock |
|---|---|---|
| end-to-end success | **3/4** | 4/4 |
| mean seconds per CV | **9.186** | 0.004 |

The failure was `synthetic_cv_04_injection.pdf`, which returned `api_error` after 2.3 s; the
other three CVs completed in 13.99 s, 8.84 s and 11.61 s. Because the same four CVs succeed
4/4 in mock mode, the failure came from the API call rather than from pipeline logic. It is
reported as measured rather than retried away: a transient-dependency failure rate is a real
property of a system that calls a hosted model, and the retry policy
(`MAX_TRANSIENT_RETRIES = 3`, exponential backoff) had already been exhausted.

**Live extraction accuracy: partially obtained on the second attempt.** A later run, with
`GEMINI_MODEL` unset, scored **1 of 4 CVs**; the other three failed with one `503 UNAVAILABLE`
and two `429 RESOURCE_EXHAUSTED`. The 429s are a free-tier quota measured per minute, which the
script was exhausting by calling four times in a row — hence `--delay`, and the separate, much
slower backoff schedule now used for 429. The figures from that one CV are real but are a sample
of one, so no accuracy claim is made from them yet.

**First attempt: a misconfiguration, not the model.** `evaluate_prompts.py --mode live` was run and all four CVs returned `api_error`
(`cvs_scored: 0`, `cvs_failed: 4` in `outputs/prompt_evaluation.json`). The recorded message
identifies the cause exactly: HTTP 404, `models/gemini-2.5-flash-lite is no longer available to
new users`. A `GEMINI_MODEL` override left over from working around an earlier 503 pointed at a
retired model name, so every call failed before the model ever saw a CV. This says nothing about
extraction quality, and the run must be repeated with `GEMINI_MODEL` unset or set to a current
model.

The episode is also the clearest argument for keeping the service's own message rather than only
an error code: `api_error` alone would have suggested an overloaded API and a pointless wait,
while the message named a configuration fault that no amount of retrying would fix. Failed
pipeline runs in `evaluate.py` now record `error_message` for the same reason.

**Prompt level** (summary; full detail in `docs/prompt_engineering.md`) — construction checks
**14/14**, planted narrative violations detected **11/11** with **0** false alarms, status
integrity preserved **6/6**.

**Prompt A/B (construction)** — both versions pass all required-rule checks and contain 3/3
injection probes under an identical configuration (same schema, temperature and input
variables); `extraction-v2`'s system prompt is 986 characters larger. No quality claim is made
offline.

**Tests** — 162 pytest tests pass, all LLM calls mocked.

## API usage and execution time

Every run now produces an `ExecutionTrace` (`src/tracing.py`), written to
`outputs/runs/<run_id>/execution_trace.json`: per-stage durations, retry counts with reasons,
error categories, and token usage **as reported by the API**. Token counts are never estimated:
when the API reports nothing, the trace says `source: "unavailable"` rather than `0`. In mock
mode no call is made, so usage is always unavailable — the measured API cost of a live screening
is therefore not yet recorded here.

## Limitations of this evaluation

1. **Live Gemini extraction accuracy is still unmeasured.** The biggest gap, and it is now a
   measured failure rather than an untried step: `evaluate_prompts.py --mode live` ran and all
   four CVs returned `api_error`. Live *integration* does work — the pipeline screened three of
   four CVs live, and the HTTP 400 schema bug, the 404 retired model and the 503 spikes were all
   found that way — but integration working is not the same as extraction being accurate. Until
   `evaluate_prompts.py --mode live` and `compare_extraction_prompts.py --mode live` complete,
   nothing here states how well Gemini extracts or how often it obeys the prompts.
2. **Tiny, author-written dataset.** 5 matching cases, 6 simulated outputs, 4 synthetic CVs, all
   written by the author of the rules. Perfect scores mean the implementation matches its own
   specification on covered scenarios — regression tests, not generalisation. A different author
   writing the cases would be the single biggest improvement to this evaluation.
3. **Simulated LLM defects ≠ real defect distribution.** The fixtures test this system's defences
   against representative failure types; real Gemini errors may differ in kind and frequency.
4. **Response time in mock mode excludes the dominant cost** (the API call).
5. **Reviewer corrections are not yet an evaluation input.** `src/review.py` records human
   disagreement, but those records are not aggregated into accuracy figures; doing so would give
   a ground truth this system's author did not write.
